# Localization (i18n)

The ds-ui interface is multilingual. Required languages are **English** (reference and fallback) and **Russian**; others are added with a single file. Architectural decision: [ADR-009](decisions.md#adr-009-multilingual-ui).

## Where things live

```
web/src/i18n/
├─ index.ts            vue-i18n initialization, language auto-discovery, language selection, pluralization
├─ naive.ts            mapping of our languages to Naive UI locales (dates, pagination, etc.)
├─ errors.ts           localized API/LDAP error messages
└─ locales/
   ├─ en.json          reference: the key set for all languages
   └─ ru.json
web/src/components/LocaleSwitcher.vue   language switcher in the header
web/scripts/check-locales.mjs           translation check (npm run check:locales, CI)
```

## How to add a language

1. Copy `web/src/i18n/locales/en.json` to `<code>.json`, where the code is a BCP 47 tag: `de`, `uk`, `pt-BR`.
2. Translate the values; set `meta.name` to the language's native name («Deutsch», «Українська») — this is how it appears in the switcher.
3. *(Optional)* add a line to `web/src/i18n/naive.ts` so that Naive UI's built-in texts (calendar, pagination) are also in this language. The list of Naive UI locales is in the library's documentation; without an entry these texts will be in English.
4. `cd web && npm run check:locales` — shows the translation percentage. Untranslated keys automatically fall back to English, so a language can be added partially.

Nothing else needs to be registered: the file is picked up automatically, the language appears in the switcher, and plural rules come from `Intl.PluralRules`.

To make a language required (CI will demand 100% translation), add its code to `REQUIRED` in `web/scripts/check-locales.mjs`.

## How to add UI strings

- In components, only via keys: `const { t } = useI18n()` → `t('overview.server.title')`. Hard-coded UI text in `.vue`/`.ts` is not allowed.
- A new key is added **at the same time** to `en.json` and `ru.json`. Keys are grouped by UI section (`nav.*`, `overview.*`, `browser.*`, …), names are `camelCase`.
- API values (enums such as `mode`, `ldapAuth`) are translated via an explicit "value → key" mapping, not by building the key from the value: this way `check:locales` sees all keys in use.
- Dynamic keys like ``t(`nav.${key}`)`` are allowed only if `key` has a strict union type (like `NavKey` in `router.ts`).

### Interpolation

`"comingInStage": "Coming in stage {stage}"` → `t('nav.comingInStage', { stage: 2 })`. The set of placeholders in every language must match English — this is checked.

### Plurals

Forms are separated by `|` in CLDR category order, keeping only those that exist in the language: **zero → one → two → few → many → other**.

| Language | Categories | Example |
|---|---|---|
| en | one, other | `"{n} suffix \| {n} suffixes"` |
| ru, uk | one, few, many, other | `"{n} суффикс \| {n} суффикса \| {n} суффиксов \| {n} суффикса"` |
| pl | one, few, many, other | `"{n} sufiks \| {n} sufiksy \| {n} sufiksów \| {n} sufiksu"` |
| de, fr | one, other (+many in fr) | `"{n} Suffix \| {n} Suffixe"` |

The final `other` form in Russian is needed for fractional numbers (1,5 суффикса); if omitted, the last specified form is used. Call: `t('overview.suffixes.count', { n }, n)`.

To see a language's categories: `node -p 'new Intl.PluralRules("pl").resolvedOptions().pluralCategories'`.

## What is not translated

- Attribute names, objectClass, DNs, OIDs, LDAP filters, `cn=config` attributes (`nsslapd-*`) — shown as is.
- Technical error details from the API (`detail`) — in English; the user sees a localized summary based on the LDAP/HTTP code, with the details as secondary text (`web/src/i18n/errors.ts`).
- ds-ui logs and directory server messages.

## Language selection

1. The user's saved choice (`localStorage`, key `dsui.locale`).
2. Browser languages (`navigator.languages`): exact tag match, then by base language (`pt-PT` → `pt-BR` if there is no other).
3. English.

Changing the language updates `<html lang>`, the tab title and the Naive UI locale.

## Texts for settings pages and templates (stages 1 and 3)

YAML descriptions of settings pages and entry templates **contain no human-readable text** — only identifiers. The texts live in the same locale files:

```json
"pages": {
  "server-limits": {
    "title": "Limits",
    "fields": {
      "nsslapd-sizelimit": { "label": "Size limit", "help": "Maximum number of entries returned by a search." }
    }
  }
},
"templates": {
  "user": { "title": "User", "description": "inetOrgPerson + posixAccount" }
}
```

Fallback chain for a field label: current language → English → attribute name; for help text: current language → English → `DESC` from the LDAP schema. This way adding a language is still "one file", and adding a page is YAML + strings in `en.json`/`ru.json`. `check:locales` will be extended with a check that every page and template has English texts.

## Dates and numbers

Formatting goes through `Intl` with the current locale (`currentLocale` from `@/i18n`). LDAP time values (GeneralizedTime) are converted to `Date` and shown in the user's locale; the original value is available in a tooltip.
